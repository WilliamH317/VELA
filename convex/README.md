## Database Schema

The schema lives in `schema.ts` and is the **single source of truth** for all database types. Convex auto-generates TypeScript types from this file — never define document types manually.

### Core Tables (Established Days 7-15)

#### `users`
Synced from Clerk on first sign-in via the `UserSetup` component.

| Field | Type | Description |
|---|---|---|
| `clerkId` | `string` | Clerk's `identity.subject` — primary user identifier |
| `email` | `string` | User email from Clerk |
| `name` | `string?` | Display name |
| `imageUrl` | `string?` | Avatar URL |
| `createdAt` | `number` | Unix timestamp (ms) |

**Indexes:** `by_clerk_id` → used for auth lookups in every query/mutation.

#### `documents`
The core content table. Every uploaded file becomes a document.

| Field | Type | Description |
|---|---|---|
| `title` | `string` | Document display name |
| `content` | `string` | Full content (may include markup) |
| `contentPlain` | `string` | Stripped plaintext — used for search and TF-IDF |
| `userId` | `string` | Owner (from `identity.subject`) |
| `type` | `"pdf" \| "text" \| "markdown"` | Source format |
| `fileId` | `Id<"_storage">?` | Convex file storage reference (for PDFs) |
| `metadata` | `object` | `{ source, uploadedAt, size }` |
| `tags` | `string[]` | User-applied tags |
| `isPublic` | `boolean` | Visibility flag |
| `status` | `"processing" \| "ready" \| "error"` | Upload pipeline state |

**Indexes:**
- `by_user` — list all user documents
- `by_user_and_type` — filter by document type
- `by_status` — find processing/errored documents

**Search Index:** `search_content` on `contentPlain`, filterable by `userId`, `type`, `isPublic`.

| Field | Type | Description |

Probabilistic membership — documents belong to clusters with confidence scores (not binary assignment).

| Field | Type | Description |

| `runId` | `Id<"clusteringRuns">` | Clustering run reference |
| `userId` | `string` | Owner |
| `membershipScore` | `number` | 0.0–1.0 probability (softmax over distances) |
| `isAmbiguous` | `boolean` | `true` if top two clusters within 15% — bridge document candidate |

#### `clusteringRuns`
Tracks each execution of the LAMINAR clustering pipeline.

| Field | Type | Description |

## Authentication & Authorization

Every Convex function that accesses user data **must** authenticate first. VELA uses Clerk JWTs verified by Convex.

### Auth Config

```typescript
// convex/auth.config.ts
export default {
  providers: [
    {
      domain: process.env.CLERK_JWT_ISSUER_DOMAIN,
      applicationID: "convex",
    },
  ],
};
```

### Required Auth Check Pattern

```typescript
// EVERY query, mutation, and action must start with this:
const identity = await ctx.auth.getUserIdentity();
if (!identity) {
  throw new Error("Not authenticated");
}
const userId = identity.subject; // This is the Clerk user ID
```

### Authorization Rule
All data queries **must** filter by `userId` to enforce tenant isolation:

```typescript
// ✅ CORRECT — scoped to authenticated user
const docs = await ctx.db
  .query("documents")
  .withIndex("by_user", (q) => q.eq("userId", identity.subject))
  .collect();

// ❌ WRONG — returns ALL users' documents
const docs = await ctx.db.query("documents").collect();
```

## Core Feature Modules

### `documents.ts` — PORT (Document Upload & Management)

**Queries:**
- `list` — All user documents, optionally filtered by type
- `getById` — Single document by ID (with auth check)
- `search` — Full-text search via `search_content` index

**Mutations:**
- `create` — Insert new document with metadata
- `update` — Modify title, tags, content
- `remove` — Delete document and associated file storage

**Key patterns:**
- PDF text extraction runs during upload (handles Convex environment constraints)
- `contentPlain` is always stripped of HTML/markup for search and TF-IDF
- File storage uses Convex's `_storage` system with `fileId` references

### `users.ts` — User Management

**Mutations:**
- `createOrUpdate` — Called by `UserSetup` component on first sign-in. Creates user record from Clerk identity if it doesn't exist.

**Queries:**
- `getCurrent` — Returns the authenticated user's record

### `ai.ts` — LIGHTHOUSE (AI-Powered Q&A)

**Actions** (not queries/mutations — actions can call external APIs):
- `generateAnswer` — Core RAG pipeline:
  1. Authenticate user
  2. Fetch selected documents (or AI-selected via relevance)
  3. Build context from document content
  4. Call Claude API with system prompt + document context + user question
  5. Stream response back with source citations

**Dual-mode operation:**
- **Smart Search:** AI automatically selects the most relevant documents
- **Manual Selection:** User picks specific documents to include as context

**Claude API integration:**
- Model: `claude-sonnet-4-20250514`
- Max tokens: 2048
- Retry logic with exponential backoff (3 retries)
- Headers: `x-api-key`, `anthropic-version: 2023-06-01`

## LAMINAR Algorithm

**LAMINAR** = Latent Association Mapping via Intelligent Natural-language Analysis and Retrieval

A chaos theory-inspired algorithm that transforms scattered documents into self-organizing knowledge clusters. Implemented entirely in pure TypeScript within Convex — no Python, no sklearn, no external ML dependencies.

### Stage 1: ARCHIPELAGOS — Self-Organization (Day 16) ✅

Documents auto-cluster into semantic groups without manual folder structure.

**Pipeline:** `documents → TF-IDF vectors → K-Means++ clustering → softmax confidence → stored results`

| File | Purpose |
|---|---|
| `laminar/tfidf.ts` | Tokenization, vocabulary building, TF×IDF vector computation |
| `laminar/kmeans.ts` | K-Means++ initialization, iterative clustering, convergence detection, silhouette scoring, `suggestK` for optimal cluster count |
| `laminar/confidence.ts` | Softmax over negated distances for probabilistic membership. Inspired by EKF sensor fusion — every measurement carries uncertainty |
| `laminar/engine.ts` | Convex action orchestrating the full pipeline. Creates `clusteringRuns` record, processes documents, stores clusters + memberships |
| `laminar/queries.ts` | Real-time queries for cluster data, membership lookups, run history |

**Key concepts:**
- **Soft membership:** A document belongs 72% to Cluster A, 18% to Cluster B — not binary
- **Ambiguity detection:** Documents with top-two clusters within 15% are flagged as bridge candidates
- **Minimum 3 documents** required to trigger clustering
- **Silhouette score** measures cluster quality (target > 0.3)

### Stage 2: CURRENTS — Temporal Pattern Detection (Day 17) ✅

Tracks how users access documents over time to predict related knowledge.

| File | Purpose |
|---|---|
| `laminar/temporal.ts` | Access trajectory estimation, periodicity detection, relevance prediction |
| `laminar/cooccurrence.ts` | Co-access tracking within sessions, co-occurrence matrix construction |

**Key concepts:**
- **Access trajectories:** Models access patterns as state estimation (rate + rate of change), not discrete events
- **Co-occurrence:** Documents accessed within the same session are linked
- **Periodicity:** Detects weekly/monthly access rhythms
- **Trajectory labels:** "Gaining momentum 📈" / "Weekly rhythm 🔄" / "Still relevant? 🤔"

### Stage 3: Cross-Document Intelligence (Day 18) 🔄

Builds a knowledge graph by fusing multiple signals into weighted edges.

| File | Purpose |
|---|---|
| `laminar/semantic.ts` | Semantic bridge detection, causal chain inference, hidden dependency surfacing |
| `laminar/graph.ts` | Multi-signal knowledge graph construction, centrality calculation |

**Four edge signals** (multi-signal fusion architecture):
1. **Content similarity** — TF-IDF cosine similarity between document vectors
2. **Temporal proximity** — How close in time documents are typically accessed
3. **Co-access patterns** — Behavioral co-occurrence from session tracking
4. **Structural links** — Shared cluster membership from ARCHIPELAGOS

**Key concepts:**
- **Bridge documents:** Span multiple clusters (high membership in 2+ ARCHIPELAGOS)
- **Attractor states:** Most-connected documents that serve as knowledge centers
- **Adaptive weights:** Signal weights can evolve based on user navigation patterns

### Stage 4: Butterfly Effect Prediction (Day 19) 📋

Predicts how changes to one document cascade through the knowledge graph.

| File | Purpose |
|---|---|
| `laminar/cascade.ts` | BFS/DFS graph traversal with decay factor, impact scoring |

### Stage 5: Fractal Wisdom Distillation (Day 20) 📋

Multi-scale pattern recognition across micro (document), meso (cluster), and macro (corpus) levels.

| File | Purpose |
|---|---|
| `laminar/fractal.ts` | Cross-scale pattern extraction, transferable insight generation |

## Convex Patterns & Conventions

### Function Types

| Type | Use Case | Can Read DB | Can Write DB | Can Call APIs | Real-Time |
|---|---|---|---|---|---|
| **Query** | Read data | ✅ | ❌ | ❌ | ✅ (auto-subscribes) |
| **Mutation** | Write data | ✅ | ✅ | ❌ | Triggers re-render |
| **Action** | External APIs, heavy compute | Via `ctx.runQuery` | Via `ctx.runMutation` | ✅ | ❌ |

### Query Pattern

```typescript
import { query } from "./_generated/server";
import { v } from "convex/values";

export const list = query({
  args: {
    type: v.optional(
      v.union(v.literal("pdf"), v.literal("text"), v.literal("markdown"))
    ),
  },
  handler: async (ctx, args) => {
    const identity = await ctx.auth.getUserIdentity();
    if (!identity) throw new Error("Not authenticated");

    if (args.type) {
      return await ctx.db
        .query("documents")
        .withIndex("by_user_and_type", (q) =>
          q.eq("userId", identity.subject).eq("type", args.type!)
        )
        .order("desc")
        .collect();
    }

    return await ctx.db
      .query("documents")
      .withIndex("by_user", (q) => q.eq("userId", identity.subject))
      .order("desc")
      .collect();
  },
});
```

### Mutation Pattern

```typescript
import { mutation } from "./_generated/server";
import { v } from "convex/values";

export const create = mutation({
  args: {
    title: v.string(),
    content: v.string(),
    type: v.union(v.literal("pdf"), v.literal("text"), v.literal("markdown")),
  },
  handler: async (ctx, args) => {
    const identity = await ctx.auth.getUserIdentity();
    if (!identity) throw new Error("Not authenticated");
    if (args.title.length === 0) throw new Error("Title cannot be empty");

    return await ctx.db.insert("documents", {
      ...args,
      contentPlain: args.content.replace(/<[^>]*>/g, "").trim(),
      userId: identity.subject,
      metadata: {
        source: "user_upload",
        uploadedAt: Date.now(),
        size: args.content.length,
      },
      tags: [],
      isPublic: false,
      status: "ready",
    });
  },
});
```

### Action Pattern (External API Calls)

```typescript
import { action } from "./_generated/server";
import { v } from "convex/values";
import { api } from "./_generated/api";

export const generateAnswer = action({
  args: {
    query: v.string(),
    documentIds: v.array(v.id("documents")),
  },
  handler: async (ctx, args) => {
    const identity = await ctx.auth.getUserIdentity();
    if (!identity) throw new Error("Not authenticated");

    // Actions read DB via ctx.runQuery
    const documents = await Promise.all(
      args.documentIds.map((id) =>
        ctx.runQuery(api.documents.getById, { id })
      )
    );

    // Actions call external APIs directly
    const response = await fetch("https://api.anthropic.com/v1/messages", {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "x-api-key": process.env.ANTHROPIC_API_KEY!,
        "anthropic-version": "2023-06-01",
      },
      body: JSON.stringify({
        model: "claude-sonnet-4-20250514",
        max_tokens: 2048,
        messages: [{ role: "user", content: `...` }],
      }),
    });

    // Actions write DB via ctx.runMutation
    await ctx.runMutation(api.ai.logQuery, { ... });

    return await response.json();
  },
});
```

### Internal Mutations (Called by Actions)

When an action needs to write to the database, use internal mutations:

```typescript
import { internalMutation } from "./_generated/server";
import { v } from "convex/values";

export const storeClusterResults = internalMutation({
  args: {
    runId: v.id("clusteringRuns"),
    clusters: v.array(v.object({ ... })),
  },
  handler: async (ctx, args) => {
    // Internal mutations skip auth — they're only callable from other server functions
    for (const cluster of args.clusters) {
      await ctx.db.insert("clusters", cluster);
    }
  },
});
```

### Client-Side Hooks

```typescript
"use client";
import { useQuery, useMutation, useAction } from "convex/react";
import { api } from "@/convex/_generated/api";

// Real-time subscription — auto-updates when data changes
const documents = useQuery(api.documents.list);
// ⚠️ Returns `undefined` while loading — always handle this!

// Fire-and-forget writes
const createDoc = useMutation(api.documents.create);

// Async operations (AI, clustering)
const runClustering = useAction(api.laminar.engine.runClustering);
```

### Index Usage Rules

1. **If you filter by it, index it.** Every `.eq()` in a `.withIndex()` call requires a matching index.
2. **Compound index field order matters.** `["userId", "type"]` supports querying by `userId` alone or `userId + type`, but NOT `type` alone.
3. **Search indexes** are separate from regular indexes. Use `.withSearchIndex()` for full-text search.
4. **Always use indexes** for queries. Never scan entire tables with `.collect()` without an index filter.

## Troubleshooting

### Common Issues

**"Not authenticated" errors:**
- Verify Clerk JWT config in `auth.config.ts`
- Ensure `CLERK_JWT_ISSUER_DOMAIN` is set correctly
- Check that the Convex provider wraps the Clerk provider in `layout.tsx`

**Schema deployment fails:**
- All `v.id("tableName")` references must point to tables defined in the schema
- Field types must exactly match what mutations write (e.g., `v.number()` won't accept a string)
- Run `npx convex dev` after every schema change

**UI doesn't update in real-time:**
- Component must use `useQuery` (not `fetch` or `useEffect`)
- The mutation must write to the same table the query reads
- Verify the Convex provider is mounted in the React tree

**LAMINAR clustering produces bad results:**
- Minimum 3 documents required (guard in `engine.ts`)
- Documents must have varied content (identical docs → 1 cluster)
- Check stop words list in `tfidf.ts` is filtering common terms
- Try adjusting K manually via `suggestK` override
- Increase max vocabulary size if domain-specific terms are being dropped

**Convex action timeouts:**
- Actions have a 10-minute timeout
- For large document sets (100+), consider batched processing
- LAMINAR engine should report progress via intermediate status updates
